## 库存缓存设计核查（用户问"是否还在 Caffeine 存库存"）

- 核查结论：**库存不进 Caffeine 三级缓存**。三级缓存（Caffeine→Redis→MySQL）只用于商品详情 `getById`；库存走独立两级路径 `getStock()` → Redis `seckill:stock:{id}` → MySQL 仅冷启动回填。代码实证：`ProductServiceImpl.getStock`(119–140) 首层即 Redis 无 Caffeine；`warmUpProduct`(153) 注释"库存不进本地缓存"；`invalidateCache`(161) 注释"库存仅存在 Redis"。
- 合理性判断：设计正确。库存是秒杀原子扣减 gate（DECR/INCR 必须打 Redis），进本地堆内存会多实例错位导致超卖；Caffeine 适合读多写少对象。且下单成功(SeckillServiceImpl ⑧)与取消订单(OrderServiceImpl.cancelOrder 101)均调 `invalidateCache` 刷新商品详情库存，无长期失真。
- 文档小修：LEARNING_GUIDE.md 第 8.3 章流程图 2592/2673 把库存误标为"三级缓存"，与文档其它段落（845/2179/2208/2410）及代码矛盾；已改为"Redis 直读库存（两级）"。

## 修正"取消回滚为何 version+1"的错误解释（用户指出）
- 原文档 9.5 节第 4 点写了一个**错误**场景："取消不 bump 版本 → B 再秒杀 `WHERE version=5` 永远命不中"——这是虚构的。实证：秒杀 ⑥（SeckillServiceImpl:123-128）用 `productMapper.selectById()` 实时从 DB 读最新 version 再当 `WHERE` 条件，B 拿到的是当前 version（已是 6），`WHERE version=6` 正常命中，不会卡死。`decreaseStockWithVersion`（ProductMapper.xml）自带 `version=version+1` 和 `stock>0` 守卫。
- 正确解释：version 是乐观锁令牌，契约是"读 V→写回仅当仍是 V"；**所有写这行的路径（扣减、回滚）都必须 version+1**，否则令牌失去对"取消 vs 秒杀"竞争的感知（本项目因库存用原子 `stock=stock-1` 恰好无害，但违反乐观锁不变量）。真正防超卖靠 Redis DECR 预扣 + MySQL 原子 `stock=stock-1 WHERE stock>0` + Redisson 同商品串行锁，version 是叠在上面的令牌。
